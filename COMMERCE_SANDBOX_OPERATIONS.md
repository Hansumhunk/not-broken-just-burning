## Tax classification review (not a tax ruling)
Stripe's current https://docs.stripe.com/tax/tax-codes lists txcd_10302000 (downloaded non-subscription digital books, permanent rights) as a candidate for substantive book-like PDFs: Boundary, Forge, Masculine Restoration and possibly 30 Days if a book rather than standalone journal forms. txcd_10503000 (downloaded standalone digital news or documents, permanent rights) is a candidate for worksheet/template packs and H.A.W.K. if entirely documents. A ZIP containing software or interactive tools could have a different classification; review final bundle and each component. Neither code is approved automatically; do not reuse membership code, mark universally nontaxable, or change registration. Confirm seller nexus/registrations and supported jurisdictions with a qualified tax professional; Stripe Tax calculates in registered jurisdictions. Confirm whether displayed USD prices exclude tax (recommended development assumption). Actual tax calculation and receipts need sandbox verification.
## Reconciliation and incident runbook
- Stop new checkouts: remove/disable NBJB_COMMERCE_SANDBOX_CHECKOUT (future live gate will require a separately reviewed change); set affected product inactive. Leave verification/download service operating for valid previous purchases and incoming webhook receipts.
- A pending order reserves one user/SKU. A Stripe idempotency key is fixed to that order; retries reuse open session; stale unknown creation attempts fail closed. Never delete a pending order to create another charge. Check Stripe session and intent; replay actual signed events through Stripe dashboard. If verified paid after an expired/failed terminal state or conflicting records, follow human reconciliation; do not create fabricated webhooks or overwrite customer history.
- Full successful refund revokes future downloads of the matching order; partial refunds flagged for review with access retained; disputes conservatively hold access even if dispute closes. Staff must verify final Stripe outcome and approve restoration using reviewed reconciliation tooling (not implemented). A manually revoked entitlement is never restored by stale same-order paid events. A new purchase after refund has new order ID. Never manually refund membership from commerce lane.
- URLs are short-lived bearer links; once issued they may be used for up to 60 seconds, and local files cannot be recalled. If leaked, disable new signing or quarantine only affected version, preserve valid customer rights and document incident. Do not expose a bucket or publish paths to Git. No permanent public link.
- If deployment fails, roll back commerce frontend only or disable checkout; never remove ledger/migration or entitlements after real sales. Restore known-good commerce worker or fix forward, preserving payment event acceptance and customer file access. Membership checkout/worker unchanged.
## Analytics (service-admin SQL only, no purchaser identifiers)
Use aggregate daily metrics and paid order ledger for product counts/revenue. Product views count authenticated details opened (respect browser privacy signal), not unique anonymous people; checkout_requested counts unique reservations, not completed checkouts; download_link_issued counts links not completed downloads. Purchase-status page runs no PostHog. Do not join these metrics to sensitive records. Gross collected includes tax; refunds net cash is not net revenue. No claim of conversion rate until compatible denominators.
## Launch gates
SQL staged and tested against disposable Postgres fixture, not full Supabase stack. Mocked Stripe payload and price tests do not constitute a real checkout or webhook. Final release requires approved files, policies, tax settings, sandbox E2E, adversarial browser/session tests, security review including actual RLS and bucket access, operational reconciliation tooling, production migration/deployment review, and explicit authorization. Production is deliberately impossible in this code: sandbox checker rejects production project and live keys; UI rejects production host, no enable config committed. A later reviewed production adapter and canary gate are needed, not merely a toggle. Do not merge prematurely.

## Data retention gate
The staged order ledger uses an auth-user foreign key with ON DELETE RESTRICT to prevent accidental erasure of purchase/financial records; this must be reconciled with account deletion and applicable retention rules before live migration. Choose an approved anonymization/retention workflow rather than silently blocking a customer deletion request. No changes to existing account deletion behavior have been deployed.
