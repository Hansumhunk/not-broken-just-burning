# Account privacy request operations and security remediation

## Account data
The limited self-service JSON export uses the same authenticated Supabase client and RLS as the member workspace: nine named datasets; explicit columns; own identity filter even for an admin; deterministic pagination; re-verification before and after the request; fail closed if any table read or identity check fails. No partial file and no token/provider identifiers in the export. It includes the signed-in member's account email and selected profile and server-side content; the file is private, unencrypted, and saved only on explicit request. Local reflections and Stripe receipts use separate export paths. Additional records can be requested through the support email. Never put a request, export, identity proof or customer data in a public repository/log.

## Deletion request — human-review workflow, not an automated deletion
1. Accept request from membership email or approved support channel. A message alone is not proof of identity; verify via a secure account-ownership procedure that does not request a password or recovery token. If identity is uncertain, stop.
2. Establish scope: device-local data vs server account; membership renewal vs separately purchased perpetual entitlements; export requested first; required legal/accounting records or disputes. Never force account deletion to stop renewal.
3. Before executing a future explicitly authorized removal, review foreign keys to auth.users, Stripe subscription state, retained records and any required retention or lawful exceptions. Make known impacts clear; resolve recurring billing separately with member authorization and confirm any effect on purchased products.
4. Obtain verified explicit removal authorization, revoke sessions, and confirm sensitive endpoints reject revoked sessions; deletion alone does not invalidate existing JWTs. Then perform a separately reviewed admin procedure. Do not implement any public endpoint that deletes users or directly changes Stripe.
5. Confirm what was removed, what remains and why, and that the support request is resolved. No customer records or subscriptions were altered by this engineering batch.

## Supabase security remediation gates
- Organization plan checked: Free. Leaked password protection requires Pro or higher per https://supabase.com/docs/guides/auth/password-security. No paid upgrade was authorized. Once founder approves billing/plan and access, enable the built-in screening in Auth settings; verify advisor clear and use a safe synthetic account in a controlled environment. Existing UI uses a minimum 8-character password; client validation is not equivalent to server leaked-password protection.
- Read-only database checks: pg_net 0.20.4 in public, extrelocatable=false, queue empty at inspection, 17 response records. Official migration guidance https://supabase.com/docs/guides/database/extensions/pg_net#troubleshooting requires DROP/CREATE and would remove queue and response data. Do not drop, flip system-catalog flags or cascade. Inventory dependency graph and active cron/trigger/job consumers (parallel storefront/automation work included), establish approved maintenance window, preserve required response data securely and verify queue remains empty after pausing writers, restore supported permissions and test synthetic approved endpoint. Obtain explicit approval for the destructive operation and verify security advisor clear post-change.
- The audio job and Stripe webhook receipt tables had RLS enabled and no anon/authenticated SELECT grants; do not add permissive policies to silence informational warnings. A read-only synthetic authenticated identity returned zero rows on all nine member datasets; real own-account export acceptance remains deferred.
- Analytics: restrict known event names and properties, force person-profile processing off, strip URL query/fragment and external referrer paths, reject malformed UTM values, avoid private member workspaces. No fabricated telemetry events sent to production; validate only with mocks before live observation.

## Verification and scope
No vendor plan, customer/user records, payment, extension or production auth configuration changed. Any future migration, deletion or signed billing acceptance must be separately authorized and verified.
