## A. Active encryption — exact protected and plaintext surfaces

**Implemented and locally synthetic-tested:** `DurableVault(..., content_key=distinct_32_byte_key)` enables a new opt-in `encrypted_payload_v1` mode for **new empty Vault databases only**. It uses maintained `cryptography`'s AES-256-GCM with fresh OS-random 96-bit nonces and canonical, authenticated context (record kind, ID, version, SHA-256). Source and derivative BLOB bytes are encrypted **before** SQLite receives them. It checks authenticated content and original plaintext hash on preview/integrity, refuses missing/wrong keys, rejects silent downgrade/upgrading of an old plaintext database, and disallows legacy plaintext `.txt` outbox export and plaintext SQLite backup. Old Phase II–IV logic remains the legacy synthetic-only mode. Protected snapshots use the existing sealed-memory backup (`.ovb`); restored protected source bytes stay encrypted when opened with the same content key.

**Not protected:** all other SQLite columns (source IDs, account/owner IDs, classification, rights evidence references, token claims, rights flags, provenance and approvals, source-content SHA-256, audit records), SQLite schema, indexes and page layout, temporary plaintext Python process memory, possible OS swap/crash dumps, backups/exports generated by *other* programs, OS administrator access, source metadata in WAL and backups **before outer `.ovb` encryption**, and a future privileged web application. No assertion of full database encryption. The system never ingests real sources in this phase.

**Blocked by operational qualification:** SQLCipher or equivalently maintained *database page encryption*, including encrypted WAL; `temp_store=MEMORY`, secure process memory and swap/crash-dump policy, page-cache and temporary file handling; dedicated key manager and encryption key epoch/rotation/recovery. SQLCipher is **not installed** in this runtime. App-level BLOB encryption is not equivalent to SQLCipher. SQLCipher manufacturer docs report encrypted WAL but warn other transient files require explicit prevention/configuration. No silent in-place migration of plaintext databases is permitted; a future conversion must operate on synthetic replicas under isolated acceptance and remove old plaintext copies/backup generations securely.

**Open key-custody requirements:** independent per-environment keys for content, backup encryption, identity verifier and approval issuer; independent external checkpoint signer; access mediated by private backend only; no JavaScript/client, CI or repo keys; founder/alternate recovery custodian rules; two-person rekey approval where appropriate; emergency revocation and stale backup decommissioning. A lost content key makes ciphertext unreadable. No escrow or HSM/OS key store was established.

## B. Independent audit, latest state and anti-rollback

**Implemented and locally synthetic-tested:** existing Ed25519 signed checkpoint binds canonical security-relevant table snapshots, audit head/sequence, explicit vault ID and monotonic checkpoint ID. Phase V expands the signed table set to include `vault_config`. `InMemorySeparateCustodian` accepts only a properly signed checkpoint matching the current Vault and with monotonically higher sequence for that vault. `restore_to_quarantine` requires the custodian's **latest** checkpoint, verifies the decrypted SQLite snapshot in *memory before disk restoration*, rejects a stale pre-revocation snapshot, and writes a private `QUARANTINE_NOT_RELEASED.json` marker on successful isolated *synthetic* recovery. `release_allowed` is always false. Rejected snapshots create no destination directory.

**Important limits:** simulated independent custody is **in the same test process**, not a remote or immutable store; privileged machine/process administrator could replace the custodian. The separate signing key is only a synthetic fixture, not protected HSM or real founder credential. Live Vault lifecycle does not yet automatically require a latest external checkpoint on every authorization/ingest/handoff; the service enforcement layer does not exist. Emergency revocation must be stored outside potentially old backups with independent append-only custody and verified before reactivation. If checkpoint unavailable/unverifiable, the future service must enter READ-DENY/QUARANTINE, never silently resume. A compromised signer requires explicit key-breach incident handling; signature verification alone cannot detect a trusted signer intentionally signing a lie.

**Required integration contract:** `latest(vault_id)` returns signed bytes, key ID, monotonic sequence and trusted source identity; a separately managed issuer signs, a distinct custodian stores; no update may decrease sequence; server validates current signing key rotation and revocation epochs. The simulated class is *interface evidence only*.

## C. Founder identity/MFA and real authority

**Implemented and locally synthetic-tested:** `PinnedAssertionVerifier` demonstrates verification of an Ed25519-signed *fake* compact identity assertion using a separately pinned test public key; rejects forged signatures, unknown `kid`, stale/expired MFA, wrong issuer/audience/account/actor/role, unsigned browser claim changes and revoked test session IDs. It returns an identity context **only**. The Vault still separately requires signed source-specific, version-specific, purpose-specific, expiring single-use permission; an identity assertion does not create property rights or release authorization.

**Not implemented:** actual IdP JWKS fetch and cache, complete OIDC/OAuth protocol, nonce/state/PKCE, key-rotation/revocation, WebAuthn challenge verification against a real authenticator, server-side immutable role storage, session-store revocation, MFA enrollment/recovery, or real founder proof. A browser-supplied `amr` flag is never sufficient without verified issuer, current server session and authenticator assurance. A real integration must bind: exact issuer, audience, account, subject, fresh `auth_time`, verified passkey or hardware MFA, session ID, short TTL, protected server-assigned role, origin-restricted challenge, and owner approval transaction. Separate **steward**, **source custodian**, **editor**, **independent reviewer**, **release operator**, **checkpoint signer** roles; least privilege. Approval signed by real founder through step-up; no self-assignable `app_metadata`/user metadata. Commercial/public release additionally requires independent rights/editorial and receiving department acceptance.

**Next gated choices:** dedicated privileged IdP vs separated restricted existing NBJB Auth; named hardware/passkey custodians; account recovery and emergency lockout process; trusted audit signer custody; explicit no-bypass checks under a backend service environment.

## D. Disaster recovery runbook — executable synthetic steps and real gaps

**Evidence:** local-memory snapshot → AES-GCM `.ovb` file; external simulated Ed25519 latest checkpoint; corrupted/wrong-key/truncated backups refused; old valid pre-revocation backup refused; matching snapshot yields quarantined local restore with no release authority. No off-device backup, no real workstation failure simulation, no production keys or actual recovery activation.

**Future operational runbook (NOT executed):**
1. Establish an incident, freeze new writes, revoke active sessions/suspect keys, preserve original evidence and record legal holds without exporting underlying source bytes.
2. On a clean, isolated device with trusted OS image, retrieve encrypted backup generations from independently controlled storage (at least two independent copies); verify backup digest, key ID, version and signed manifest without exposing source content to untrusted providers.
3. Fetch **latest** separately held trusted checkpoint and revocation epoch from independent custodian; if missing, disputed or signing-key compromised, deny restoration/activation and escalate to founder plus independent custodian.
4. Decrypt only with approved recovered keys into protected/quarantined environment; validate DB/foreign keys, page encryption and process-memory safeguards, source/derivative hashes, source rights evidence, approval expirations and access role inventory.
5. Compare restored audit digest/seq against latest checkpoint; if stale, either independently replay **authenticated post-backup events including revocations** and build a new signed checkpoint, or refuse operational reactivation. **Current prototype refuses**; it does not safely replay events.
6. Invalidate all older sessions and tokens; verify changed privileges, legal holds, deletion retention and KMS key version, independent reviewer sign-off and founder step-up approval.
7. Separately test read-only then controlled write operations and incident rollback. Record restored point in time, measured elapsed duration and irreversible gaps. Never reopen production on green database integrity alone.
8. Check separately authorized distribution systems remain off. Resume only with explicit deployment/release authorization.

**Founder choices (options, not approved targets):** RPO 24 h with daily protected backups / 4 h with multiple daily incremental generations / <= 1 h with dedicated continuous change capture and an externally durable revocation feed. RTO 48–72 h for manual restored local workstation / 8–24 h with staged secure device + custodians / <=4 h requiring paid infrastructure, standby and tested automation. Costs/requirements rise as RPO/RTO shrink. Prescribe separate retention schedule/legal hold before deletions; never equate crypto-shredding with guaranteed erasure of all backup copies. Must test separately controlled full restore before saying disaster recovery is operational.

## F. Rights, provenance and department boundaries

The existing Vault requires an explicitly bound source ID/version/content digest/owner/account/purpose/scope/expiry/rights-evidence ref. The program holds immutable-by-trigger source and derivative versions, concept lineage, a source-grant per action, and only metadata-only department handoff previews. Source possession or SHA-256 does not establish authorship, ownership, derivative rights, disclosure authority, publication authority or commercial license. Actual documentary rights evidence needs private verification, retention rules, source classification (third-party/legal/clinical/family restricted) and contradiction/revocation handling before any confidential ingestion.

Release pipeline stays **source registration → rights review → founder processing permission → review-only derivative → independent editor/rights review → target department acceptance → separate marketing/commerce/publication gate**. No live Brevo, Stripe, social, website, AI service, Supabase Storage or auto-publishing connector. Executive Command sees aggregate status only; issue #274 must never receive confidential source identifiers.
